### [x] M1-17c Key-boundary decisions: h2c, fragments in the target, keyed cookie size
- Plan: M1 (decisions of 2026-09-28) · Size: M · Depends on: M1-17
- Read: 01 FR-UPG-1, FR-VAL-1, FR-VAL-3; 04 §3.7 and the cookie section; 06 T-13, T-44 and §6
- Touch: internal/keys/{validate.go,cookie*.go,*_test.go}, internal/keys/testdata/fuzz/, weirhttp/weirhttp_test.go, docs/01, docs/04, docs/06
- Tests: TestH2CUpgradeServedNormally (keys and weirhttp: `Upgrade: h2c` alone is served and keyed like a plain request; `h2c, websocket` still routes around), TestFragmentInTargetRejected (`#` in path or query, and `?` in path, give `path`/`query` reasons), TestKeyedCookieLimitCountsKeyedPairs (a 4 KiB analytics cookie next to a keyed `lang` keeps `lang`)
- AC: FR-UPG-1, FR-VAL-1 and FR-VAL-3 reworded; fuzz seeds for each new input shape; the docs/06 §6 checklist is in the PR; `make check` passes
- Notes: decisions and rejected options.
  - h2c: RFC 9110 §7.8 lets a server ignore `Upgrade`, and `curl --http2 http://` got 501. Only an `Upgrade` whose sole token is `h2c` (any case) is ignored. `Upgrade` and `HTTP2-Settings` are dropped as hop-by-hop, so key and forward stay equal. Rejected: ignoring every `Upgrade` (breaks WebSockets through `Middleware`), and keeping 501 (breaks a common client).
  - `#`: a raw `#` is invalid in origin-form (RFC 9112 §3.2), and origins read it as a fragment, so `/a#x` fragments the cache. Rejected: percent-encoding (it changes what the client meant into a literal `#` path byte), and keeping it.
  - Cookie: the 1 KiB limit applies to the keyed pairs only. The scan is linear and bounded by the server's header limit (P5: state that bound in 04). The forwarded Cookie carries only keyed pairs, so an absent `lang` was never poisoning, but it made common traffic lose its language. Rejected: a separate larger Cookie limit (only moves the cliff).

### [x] M1-17d Storability decisions: s-maxage permission, markers after unkeyed input, remote-store clock
- Plan: M1 (decisions of 2026-09-28) · Size: M · Depends on: M1-17c
- Read: 01 FR-STO-5, FR-STO-12; 06 T-8, T-31; 05 §8; CLAUDE.md hard rule 6
- Touch: storable.go, serve.go (setMarker), *_test.go, docs/01, docs/05, docs/06, CLAUDE.md
- Tests: TestAuthorizationNeedsValidSMaxage (`s-maxage=abc` or two differing `s-maxage` values do not permit storing an `Authorization` response; `public` and `must-revalidate` still do), TestNoMarkerAfterUnkeyedInput (a request that forwarded a `Forward.Allow` field or ran under `ForwardAll` plants no marker; trace headers alone still do)
- AC: FR-STO-5 and FR-STO-12 reworded; 05 §8 runs remote `ExpiredIsNotFound` only under the `integration` build tag, and hard rule 6 names that tag next to `load`; `make check` passes
- Notes: decisions and rejected options.
  - `s-maxage`: RFC 9111 §4.2.1 treats invalid or duplicate directives as unusable, so they cannot grant the §3.5 permission. With T-8, a zero-lifetime entry could otherwise be served stale to another user. Rejected: also refusing stale serving (redundant once the entry is not stored).
  - Markers: a client-controlled unkeyed field lets one client plant a 30 s marker for a hot key, which turns stampede protection off for everyone and can be renewed. The cost is that `Forward.Allow` users lose markers on those requests: an uncacheable URL coalesces, and followers re-enter (FR-COA-5). That cost is opt-in; the default (trace headers only) keeps markers. Document the trade-off in FR-STO-12. Rejected: suppressing markers only under `ForwardAll` (misses `Forward.Allow`).
  - Remote-store clock: Valkey expiry runs on the server clock, so synctest cannot fake it, and an `integration` tag keeps rule 6 unexceptional. Rejected: a blanket exemption.

### [x] M1-17e Response decisions: hop-by-hop in fetch, 304 metadata, Pragma
- Plan: M1 (decisions of 2026-09-28) · Size: M · Depends on: M1-17d
- Read: 01 FR-STO-11, FR-SRV-3, FR-SRV-8, §14.5; 04 §6 fetch; internal/httpcc request parsing
- Touch: fetch.go, conditional.go, internal/httpcc/*.go, *_test.go, docs/01, docs/04
- Tests: TestFetchDropsHopByHop (miss, pass-through and stream responses from `Serve` carry no hop-by-hop or `Connection`-named fields), TestFreshenKeepsRepresentationMetadata (a 304 with a different `Content-Encoding` or `Content-Type` does not relabel the stored body), TestPragmaIgnoredWithCacheControl (under `HonorRevalidation`, `Pragma: no-cache` forces validation only when no `Cache-Control` is present)
- AC: a new FR-FWD requirement for response hop-by-hop; FR-SRV-3 and FR-SRV-8 reworded; `make check` passes
- Notes: decisions and rejected options.
  - Hop-by-hop: strip once in `fetch`, the single origin path (P3), so every adapter gets it. Keep the weirhttp `WriteResponse` strip too: the adapter owns the connection, and the second strip costs one map walk. Rejected: adapter-only (the Caddy adapter would repeat it).
  - 304: a stored body is valid only with its own `Content-Encoding` and `Content-Type`, and RFC 9110 §15.4.5 says a 304 should not carry other representation metadata. Keeping the stored values stays self-consistent, even for weak ETags. Rejected: dropping the entry and refetching (costs an origin call when an origin misbehaves).
  - Pragma: RFC 9111 §5.4 deprecates it, and every browser that sends it also sends `Cache-Control`. Honoring both only widens how clients can force origin traffic under `HonorRevalidation`. Rejected: honoring both (the status quo).
