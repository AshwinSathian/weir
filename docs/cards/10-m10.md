### [x] M10-08 Group tags skip the invalid plane
- Plan: M10.9 · Size: M · Depends on: M10-01
- Read: 05 §1 (capability interfaces), E-3, E-7 to E-10; 06 T-23, T-29 and §6; 04 §3 (entry tags), §4.3; store/memory/epochs.go; storeguard.go (`newestEpoch`); entry.go (`buildEntry`)
- Touch: store/store.go, store/memory/epochs.go, store/memory/store.go, store/storetest, storeguard.go, docs/05 (E-8, capability list), docs/06 (T-29), docs/04 §3, tests
- Tests: TestSharedTagsSkipInvalidPlane (memory), TestInvalidationFloodLeavesGroupsServable (engine), a storetest case run when the capability is present
- AC: a URI invalidation flood that fills the invalid plane never makes a group's entries read as invalidated; a soft or hard epoch written to a group tag is still found (`EpochNeverUnderInvalidates` passes unchanged); a store without the capability behaves as today; hit path allocations unchanged; `make check` passes
- Notes: decided 2026-10-06, delegated by Ashwin; reasons in STATUS "Decided 2026-10-06 (M10-01)". Security-sensitive: answer the 06 §6 checklist in the PR. The engine writes only soft and hard epochs to group tags, so any invalid-plane match on one is a false positive, and it hits every entry of the group at once (invalidated entries are not served stale on error, so the burst sheds). Add an optional capability to `store`, one call so a remote store keeps one round trip: `SharedTagEpochs{ NewestEpochShared(ctx, tags, shared []Tag, since time.Time) (Epoch, bool, error) }`, equal to `NewestEpoch` over both lists except that a tag in `shared` never matches in `EpochInvalid` mode. `Entry.Tags` is `[global, URI, groups...]` (entry.go); state that order in 04 §3 and split on it in `storeGuard.newestEpoch`, falling back to `NewestEpoch` when the store lacks the capability. Do not raise the default `EpochSlots`: 2^22 costs 32 MiB against a 16 MiB minimum store and an attacker undoes it with 8 times the requests.
